# Reparación y auditoría de backups — 2026-10-09

Fase 01, después de validar y publicar la fase 00 (`945722a`).

## Causas y cambios

- El backup local falló realmente en la instancia principal. `pg_dump` buscaba
  `/nonexistent/.postgresql/root.crt`: la URL de las herramientas PostgreSQL
  omitía `DB_SSLROOTCERT`, aunque SQLx sí utilizaba esa CA. La URL de backup y
  restore incorpora ahora la CA, conserva `verify-full` y respeta una CA
  explícita en la URL. No se relajó TLS ni se modificaron claves.
- El incremental anterior era otro snapshot completo. Los puntos nuevos
  almacenan deltas cifrados de base de datos y media. Reconstruyen cada archivo
  desde su parent y verifican SHA-256 de base y resultado, manifiestos y cadena.
  Conservan la lectura de snapshots anteriores. Los nombres incluyen UUID para
  impedir que dos trabajos del mismo segundo sobrescriban un ancestro.
- El diálogo de copia inmediata permite seleccionar automática, completa o
  incremental sin modificar la programación. El panel recoge el resultado
  asíncrono y no conserva el aviso «en curso» tras un fallo.
- El acceso al panel admin reveló 429 en `/ws/conexiones/`: HTTP y WS compartían
  contador de conexiones. Nginx conserva el límite WS de diez por IP en una
  zona independiente; las cuotas HTTP, de chat, autenticación y contacto siguen
  activas. Se comprobó el nuevo comportamiento en la pila principal.

Los destinos externos de la instancia principal no están configurados y no

La estrategia no promete recuperar sesiones activas ni caché tras un desastre.

[BACKUP_RESTORE.md](../BACKUP_RESTORE.md); no ofrecen WAL/PITR ni un drill de
pérdida total del equipo. Evidencia local en `.run/order-20261009/01/`.
